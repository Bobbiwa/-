# TypeScript 如何通过类型守卫、可辨识联合和穷尽检查保证分支安全？

## 问题

什么是 TypeScript 的类型收窄？常见类型守卫有哪些？如何设计可辨识联合，并借助 `never` 保证新增业务分支时编译器能够提醒遗漏？

> [!note]- 查看答案
>
> ## 30 秒口述答案
>
> 类型收窄是 TypeScript 根据运行时判断和控制流，把一个宽类型在特定分支里缩小成更具体的类型。常见守卫有 `typeof`、`instanceof`、`in`、相等判断、`Array.isArray` 和返回类型谓词的自定义函数。业务状态最好设计成可辨识联合：每个成员都有同名的字面量字段，例如 `role: "action" | "branch" | "loop"`。`switch` 处理完所有成员后，把默认分支交给 `never`，新增成员却漏写分支时就会在编译期报错。
>
> ## 详细原理
>
> ### 1. 收窄依赖运行时证据和控制流
>
> 联合类型只允许直接执行所有成员都支持的操作。条件判断提供新的证据后，TypeScript 的控制流分析会沿着分支、提前返回和赋值关系更新变量类型。例如 `typeof value === "string"` 后才能安全调用字符串方法。
>
> 常见守卫各有边界：
>
> - `typeof` 适合原始类型，但 `typeof null === "object"`，检查对象时必须排除 `null`；
> - `instanceof` 依赖运行时构造函数与原型链，不能检查只存在于编译期的 `interface`；
> - `in` 检查属性是否存在于对象或其原型链上，不等于属性值有效；
> - 真值判断会同时排除 `0`、`""`、`false`，业务若允许这些值就不能笼统使用；
> - 自定义类型谓词 `value is T` 的实现由开发者负责，谓词写错会让编译器得到错误前提。
>
> ### 2. 可辨识联合让数据模型与分支一一对应
>
> 可辨识联合要求每个成员拥有一个共同字段，并且该字段是互斥的字面量类型。与“一个大接口加很多可选字段”相比，它能表达：当 `role` 是 `branch` 时一定存在 `paths`，当 `role` 是 `loop` 时一定存在 `children`。检查 `role` 后，TypeScript 会自动得到对应成员，无需到处使用非空断言。
>
> 辨识字段应稳定且语义明确。若后端传入任意字符串，仍需先在运行时验证，不能因为前端声明了联合类型就假设外部数据正确。
>
> ### 3. `never` 把遗漏变成编译错误
>
> 当所有联合成员都被排除后，剩余变量的类型是 `never`。默认分支调用 `assertNever(step)`，当前联合完整时可以通过；将来加入新成员而忘记处理时，新成员不能赋给 `never`，编译器便会指出遗漏位置。
>
> 这比默默返回默认值更适合核心状态机和协议转换，因为默认值可能掩盖新业务状态。对于确实需要向前兼容的外部协议，则应显式设计 `unknown` 分支并记录降级策略，而不是假装穷尽。
>
> ## TypeScript 示例（TypeScript 5.9，Node.js 或浏览器）
>
> ```typescript
> interface ActionStep {
>   role: "action";
>   id: string;
>   operation: string;
> }
>
> interface BranchStep {
>   role: "branch";
>   id: string;
>   paths: Step[][];
> }
>
> interface LoopStep {
>   role: "loop";
>   id: string;
>   children: Step[];
> }
>
> type Step = ActionStep | BranchStep | LoopStep;
>
> function assertNever(value: never): never {
>   throw new Error(`未处理的步骤：${JSON.stringify(value)}`);
> }
>
> function countSteps(steps: readonly Step[]): number {
>   return steps.reduce((total, step) => {
>     switch (step.role) {
>       case "action":
>         return total + 1;
>       case "branch":
>         return total + 1 + step.paths.reduce(
>           (sum, path) => sum + countSteps(path),
>           0,
>         );
>       case "loop":
>         return total + 1 + countSteps(step.children);
>       default:
>         return assertNever(step);
>     }
>   }, 0);
> }
>
> const workflow: Step[] = [
>   { role: "action", id: "a1", operation: "fetch" },
>   {
>     role: "loop",
>     id: "l1",
>     children: [{ role: "action", id: "a2", operation: "send" }],
>   },
> ];
>
> console.log(countSteps(workflow)); // 3
> ```
>
> 如果新增 `interface DelayStep { role: "delay"; ... }` 并把它加入 `Step`，但没有给 `switch` 添加 `delay` 分支，`assertNever(step)` 会产生类型错误。
>
> ## 常见追问
>
> 1. **类型谓词和类型断言有什么区别？** 谓词函数应通过运行时逻辑提供可复用证据；断言不执行检查，只覆盖编译器判断。
> 1. **为什么不把所有成员字段都放进一个接口并标成可选？** 那样无法表达字段之间的关联，分支内部仍会遇到 `undefined`，也容易构造出业务上无效的组合。
> 1. **`default` 分支直接抛错是否等于穷尽检查？** 运行时能兜底，但只有让剩余值满足 `never` 才能在新增联合成员时得到编译期提醒。
>
> ## 易错点
>
> - 用 `if (value)` 收窄时误伤合法的 `0`、空字符串或 `false`。
> - 认为 `in` 已经验证了属性值的类型，实际上还需继续检查值。
> - 编写不可靠的 `value is T` 谓词，让声明与实际检查不一致。
> - 用多个布尔字段表达互斥状态，产生“同时为真”或“全部为假”的非法组合。
> - 在 `switch` 的默认分支返回普通默认值，导致新增联合成员时静默漏处理。
>

>
> 以下结论基于 2026-08-11 对 `my-ipaas` 当前代码的只读检查，只代表代码存在：
>
> - **已实现：步骤可辨识联合。** `src/pages/canvas/types.ts` 将 `Step` 定义为 `ActionStep | BranchStep | LoopStep`，以 `role` 区分普通步骤、分支容器和循环容器。
