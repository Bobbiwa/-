> 目标：脱离代码，只用一张纸＆一根笔，绘制项目框架，内容边界。

“绘制战术地图”本质上是在你的大脑里建立一个“抽屉分类系统”。

面试时最怕的不是不会，而是面试官问了一个点，你脑子里像一团乱麻，不知道去哪一段代码里找答案。战术地图的作用就是：**无论面试官问什么，你都能瞬间定位到它是哪个“抽屉”里的事，并果断告诉面试官“这个层级只管什么，不管什么”。**

你可以拿出一张白纸，跟着以下三个具体动作来画，画完之后你的底气会产生质的飞跃：

### 动作一：画出系统边界（划分四大抽屉）

在纸上画四个大框，把我们项目最核心的架构填进去。你只需要在框里写关键词，千万不要写具体的代码：   

1. **视图与交互层 (React 层)**
   - **核心内容**：DOM 节点、SVG 连线、拖放组件 (`dnd-kit`)、视口相机 (`Camera` 平移缩放)。   
   - **它的使命**：只负责“把算好的坐标渲染出来”和“收集用户的鼠标动作”。
2. **几何计算层 (纯粹的引擎层)**
   - **核心内容**：`layoutFlow` 核心纯函数、节点尺寸计算、连线折线生成。   
   - **它的使命**：吃进一堆业务数据，吐出一张带有 `x/y` 坐标的蓝图 (`LayoutResult`)。   
3. **状态真理层 (Zustand 层)**
   - **核心内容**：递归的 `Step[]` 数组流、各个解耦的 slice（画板、调试、配置面板）。   
   - **它的使命**：维护业务最底层的绝对真相。节点到底排在第几个，全看这里的数组索引，而不是屏幕上的像素位置。   
4. **服务端防御层 (Node.js/AI 层)**
   - **核心内容**：AI Prompt 组装、能力目录（Catalog）注入、大模型 JSON 产物拦截与编译器。   
   - **它的使命**：确保 AI 生成的废话或假代码绝对进不了前端的业务树。   

### 动作二：确立“什么绝对不能干”（极其重要的高级思维）

初级开发背 API，高级开发定边界。在你的这四个大框旁边，用红笔写下每个层的“绝对禁区”。这也是面试官最喜欢挖坑的地方：

- 在**视图交互层**旁边写：**绝不允许在滚轮事件里直接改所有节点的具体坐标！**（只改父级容器的 `transform`）。   
- 在**几何计算层**旁边写：**绝不允许在这里访问 DOM 去测量宽高！**（节点尺寸全部用常量写死，保证它是纯函数，不会触发反复重绘）。   
- 在**状态真理层**旁边写：**绝不持久化保存任何节点的 x/y 像素！**（只存业务逻辑里的数组先后顺序 `index`）。   
- 在**服务端防御层**旁边写：**绝不把大模型吐出的文本直接丢给前端渲染！**（必须先经过校验器洗一遍）。   

### 动作三：连线（跑通因果流转）

在框和框之间画箭头，标明数据是怎么流动的。比如用户拖拽一个节点：

- **视图层**（拖拽松手，触发事件） ➡️ 告诉 **状态层**（把节点从数组 index A 挪到了 index B） ➡️️ **状态层**数据变了，触发 **几何计算层**（重新按顺序算一遍所有的坐标） ➡️ 算好后交回给 **视图层**（DOM 和 SVG 更新位置）。

### ⚠️ 操作时的核心注意事项：

1. **不要陷入变量名的回忆**：如果想不起来某个函数叫什么，直接在纸上写“那个用来算坐标的函数”、“那个用来合并帧的引用”。只要架构是对的，面试官根本不在乎你拼错一个函数名。
2. **警惕“伪需求”防御**：面试官可能会拿他们日常开发 React Flow（一种通用的、可以自由连线的拖拽库）的痛点来考你。你必须理直气壮地拿着你的地图反驳：“我们的场景不是自由连线画布，而是**受限垂直流程树**，所以我故意没做自由坐标系，而是选择了单向数据流。”这种“Trade-off（架构取舍）”的回答，是极其加分的。

### 💡 怎么用这张图来“秒杀”面试官的陷阱题？

我们立刻来演练一下。面试官常常会故意抛出一些“混淆边界”的问题，诱导你掉进坑里。有了这张图，你只需做“抽屉定位”。

**🔥 陷阱问题 1：“你们画布放大缩小时，Zustand 里的状态会频繁更新，导致整个页面严重卡顿吗？”**

- **你的思考路径：** 放大缩小属于哪个框？【1️⃣ 视图层】。Zustand 是哪个框？【3️⃣ 状态层】。这两个框有直接关系吗？没有。   
- **你的满分回答：** “绝对不会。在我们系统的设计里，视口缩放完全是【视图层】的内部行为，它改变的仅仅是最外层父容器的 CSS `transform` 比例和局部的 Ref 相机状态。业务节点的顺序没变，所以根本不会去触碰 Zustand 的【状态层】，也不会触发 `layoutFlow` 重新计算。这就做到了交互渲染与业务状态的绝对物理隔离。”   

**🔥 陷阱问题 2：“如果有个节点的文本名字特别长，你们是怎么计算它宽度的？会不会导致后面的节点连线对不齐？”**

- **你的思考路径：** 算宽度属于哪个框？【2️⃣ 几何计算层】。它的绝对禁区是什么？不准去 DOM 测尺寸！   
- **你的满分回答：** “在我们的架构里，几何计算是一个纯函数，它严禁去 DOM 层测量实际的文本排版宽度。为了保证递归布局的绝对稳定，我们对节点尺寸和标签宽度采用了定宽策略（常量配置）。长文本直接用 CSS 截断省略，坚决不让 UI 层的不可控因素反向污染我们的几何引擎，这保证了我们的连线永远精准穿过节点中心。”
