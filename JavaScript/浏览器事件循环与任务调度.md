# 浏览器事件循环如何调度 task、microtask 与渲染？

## 问题

浏览器中的同步代码、`setTimeout`、Promise 回调、`queueMicrotask` 和页面渲染分别如何调度？请解释 task 与 microtask 的执行关系、预测一段代码的输出，并说明它与 Node.js 事件循环有什么不同。

<h2>30 秒口述答案</h2>
<p>浏览器事件循环每轮会从某个 task queue 取一个可运行 task 执行；当前 JavaScript 执行栈清空后，会执行 microtask checkpoint，把 microtask queue 一直清空，包括期间新加入的 microtask。Promise reaction 和 <code>queueMicrotask</code> 属于 microtask，timer 到期后排入 task。microtask 清空后，浏览器才可能在合适的渲染时机更新页面，但不是每完成一个 task 都一定渲染。规范术语是 task，“宏任务”只是常见教学叫法。Node.js 有 libuv phases 和 <code>process.nextTick</code> 等额外规则，不能直接套用浏览器模型。</p>
<h2>详细原理</h2>
<h3>1. ECMAScript 与浏览器宿主各自负责什么</h3>
<p>ECMAScript 规范定义执行上下文、Job、Promise reaction 等语言机制，但不会定义 DOM、timer 或浏览器何时绘制。WHATWG HTML Standard 把 ECMAScript 的 Promise jobs 接入浏览器的 microtask queue，并定义 event loop、task queue、timer 和渲染更新等宿主行为。</p>
<p>因此，“Promise 回调是 microtask”是 Web 宿主整合后的说法；<code>setTimeout</code> 也不是 ECMAScript 语法，而是浏览器和 Node.js 分别提供的宿主 API。</p>
<h3>2. task 不是单一的全局 FIFO 队列</h3>
<p>HTML 规范使用 <strong>task</strong> 与 <strong>task queue</strong>。常说的“宏任务”便于和 microtask 对比，但不是 ECMAScript 或 HTML Standard 的正式术语。</p>
<p>一个 event loop 可以有多个 task queue。相同 task source 的任务需要维持规范要求的顺序，而浏览器从哪个非空队列选择任务可受实现调度影响。所以不能把所有点击、网络、timer 和消息任务简单画成一个永远严格 FIFO 的“宏任务队列”。</p>
<p>常见 task 来源包括：</p>
<ul><li>初始执行一段 classic script；</li><li>timer 到期后的回调；</li><li>用户交互事件；</li><li>消息事件和部分网络事件。</li></ul>
<p><code>setTimeout(callback, 0)</code> 的 <code>0</code> 表示最短等待意图，不是立即执行，也不保证精确延迟；只有满足 timer 条件后，回调才有机会作为 task 被调度。</p>
<h3>3. microtask checkpoint 会清空队列</h3>
<p>Promise 的 <code>then</code>、<code>catch</code>、<code>finally</code> reaction，以及 <code>queueMicrotask</code> 注册的回调，会进入 microtask queue。当前 task 的 JavaScript 栈清空后，浏览器在规定的时机执行 microtask checkpoint：按入队顺序不断取出 microtask，直到队列为空。microtask 执行期间新加入的 microtask 也会在本次 checkpoint 中继续执行。</p>
<p>这解释了两个现象：</p>
<ol><li>已 fulfilled Promise 的 <code>then</code> 仍然晚于当前同步代码执行。</li><li>持续递归加入 microtask 会长期推迟后续 task 和渲染，造成页面无响应。</li></ol>
<h3>4. 渲染是“可能发生”，不是固定插入点</h3>
<p>对 Window event loop 而言，microtask checkpoint 之后，浏览器会在合适的 rendering opportunity 更新渲染；<code>requestAnimationFrame</code> 回调属于渲染更新流程，不应简单归为普通 task 或 microtask。浏览器可能因为刷新率、页面是否可见或性能策略跳过某次渲染，所以“每执行一个 task 就一定渲染一次”是错误结论。</p>
<p>同一个 task 内连续修改 DOM，随后又在 microtask 中修改 DOM，用户通常只会看到 microtask 结束后的最终状态，因为绘制还没有机会发生。若 microtask 过多，也会阻塞绘制。</p>
<h3>5. Node.js 不能照搬浏览器结论</h3>
<p>Node.js 的事件循环围绕 libuv phases 组织，并且有 <code>process.nextTick</code> 等浏览器没有的队列。Node.js 的 timer 阶段细节也可能随 Node/libuv 版本变化。只含标准 Promise 与同步代码的局部推理通常相似，但一旦涉及 <code>process.nextTick</code>、<code>setImmediate</code>、I/O 或 timer phase，就必须按指定 Node.js 版本和上下文分析。</p>
<h2>JavaScript 示例</h2>
<p>运行环境：现代浏览器控制台。示例只使用 Web 事件循环语义，不使用 Node.js 专有 API。</p>
<pre><code class="language-javascript">console.log(&#39;script start&#39;);&#10;&#10;setTimeout(() =&gt; {&#10;  console.log(&#39;timer&#39;);&#10;}, 0);&#10;&#10;Promise.resolve().then(() =&gt; {&#10;  console.log(&#39;promise 1&#39;);&#10;  queueMicrotask(() =&gt; console.log(&#39;nested microtask&#39;));&#10;});&#10;&#10;queueMicrotask(() =&gt; {&#10;  console.log(&#39;microtask 1&#39;);&#10;});&#10;&#10;console.log(&#39;script end&#39;);</code></pre>
<p>输出：</p>
<pre><code class="language-text">script start&#10;script end&#10;promise 1&#10;microtask 1&#10;nested microtask&#10;timer</code></pre>
<p>推导过程：</p>
<ol><li>当前 script 的同步语句先执行，timer 回调等待成为后续 task。</li><li>Promise reaction 先于 <code>microtask 1</code> 入队，所以先输出 <code>promise 1</code>。</li><li><code>promise 1</code> 中加入的 <code>nested microtask</code> 排到已有 <code>microtask 1</code> 后面。</li><li>本轮 microtask queue 清空后，timer task 才有机会执行。</li></ol>
<h2>常见追问</h2>
<ol><li><strong>microtask 中继续加入 microtask，会等到下一轮事件循环吗？</strong> 不会；当前 checkpoint 会继续清空队列，因此递归加入可能让 task 和渲染饥饿。</li><li><strong><code>setTimeout(fn, 0)</code> 为什么不是立即执行？</strong> 它需要先经过 timer 条件，再排入 task queue，并等待当前 task 和随后的 microtask checkpoint 完成；系统调度还可能增加延迟。</li><li><strong><code>requestAnimationFrame</code> 是“宏任务”吗？</strong> 不宜这样归类。HTML Standard 把 animation frame callbacks 放在更新渲染流程中，它既不是普通 task queue 中的 task，也不是 microtask。</li></ol>
<h2>易错点</h2>
<ul><li>把“宏任务”说成 ECMAScript 的正式术语；规范讨论浏览器调度时使用的是 task。</li><li>认为浏览器只有一个严格 FIFO 的 task queue，忽略不同 task source 和实现调度。</li><li>认为 microtask checkpoint 只处理检查开始前已有的任务；实际上会持续处理期间新入队的 microtask。</li><li>认为 <code>setTimeout(fn, 0)</code> 会在 0 毫秒后准时执行，或认为 Promise 回调是同步执行。</li><li>固定背诵“每个 task 后必定渲染”，忽略 rendering opportunity 和浏览器调度条件。</li><li>用浏览器规则推断 <code>process.nextTick</code>、<code>setImmediate</code> 或 Node.js I/O 回调顺序。</li></ul>
