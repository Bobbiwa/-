这道题是检验前端“性能优化”基本功的试金石。

很多初中级开发者有一种“性能强迫症”：既然每次渲染都会重新创建函数和变量，那干脆给所有的函数套上 `useCallback`，所有的变量套上 `useMemo`，不就完美了吗？

如果在面试时你流露出这种想法，面试官会直接给你打上“缺乏底层常识”的标签。因为**优化本身是需要成本的**。

我们用“买保险柜”来比喻：`useMemo` 和 `useCallback` 就是保险柜。如果你为了保护一张 1 块钱的纸币（极简的计算），花 100 块钱买了个保险柜（依赖对比的内存和计算开销），这就是典型的**负优化**。

# useMemo / useCallback 何时用？何时坚决不用？

在 React 开发中，`useMemo` 和 `useCallback` 是最常用的性能优化 Hooks，但也是最容易被滥用的 Hooks。本文将通过示例详细说明它们的适用场景和“坚决抵制”的场景。

## 一、它们是做什么的？

简单来说，它们的作用都是 **“缓存（记忆化，Memoization）”**：

- **useMemo**：缓存**计算结果（值）**。只有当依赖项改变时，才会重新计算。
- **useCallback**：缓存**函数引用**。只有当依赖项改变时，才会返回一个新的函数引用。

本质上，`useCallback(fn, deps)` 等价于 `useMemo(() => fn, deps)`。

## 二、何时推荐使用？（正确场景）

### 1. 计算代价极其昂贵时（仅限 useMemo）

如果某个数据的计算需要遍历巨大的数组、执行复杂的算法等，为了避免每次渲染都重新计算，必须使用 `useMemo`。

**示例：**

```react
function DataGrid({ rows, filterOptions }) {
  // 假设 filterRows 极其耗时
  const visibleRows = useMemo(() => {
    return rows.filter(row => row.status === filterOptions.status);
  }, [rows, filterOptions]); // 只有当 rows 或 filterOptions 变化时才会重新计算

  /* 渲染数据 */
  return <div>{visibleRows}</div>;
}
```

### 2. useCallback/useMemo配合React.memo（核心）

> `useCallback` 和 `useMemo` 很大程度上就是为了配合它而存在的。

React 默认的“连坐机制”（痛点）：**只要父组件重新渲染（比如状态改变了），它的所有子组件都会跟着重新渲染。** 哪怕父组件传给子组件的数据（props）根本没有任何变化，子组件也会被“连坐”，无脑重新执行一遍。

#### `React.memo` 是什么？

`React.memo` 是一个**高阶组件**（本质上是一个函数，你把你的组件传给它，它还给你一个增强版的组件）。

它的作用就是给子组件穿上一件“防弹衣”。它会对 React 说： 👉 **“每次父组件更新时，请先检查一下传给我的 props 有没有变。如果 props 和上次一模一样，就跳过我的渲染，直接用上次渲染好的结果！”**

**示例：**

```react
import React, { useState } from 'react';

// ✨ 给子组件穿上防弹衣
const Child = React.memo(function Child({ text }) {
  console.log("💣 子组件重新渲染了！");
  return <div>我是子组件，收到的文本是: {text}</div>;
});

function Parent() {
  const [count, setCount] = useState(0);
  const [text, setText] = useState("你好");

  return (
    <div style={{ border: '2px solid black', padding: '20px' }}>
      <h2>父组件 Count: {count}</h2>
      <button onClick={() => setCount(count + 1)}>点我 Count + 1</button>
      
      {/* 子组件只依赖 text 状态 */}
      <Child text={text} />
    </div>
  );
}
```

**运行结果：** 现在你疯狂点击“点我 Count + 1”按钮，控制台**再也不会**打印 `💣 子组件重新渲染了！`。 因为 `React.memo` 发现：上次传进来的 `text` 是 "你好"，这次还是 "你好"，完全没变，直接拦截了渲染！



#### 核心暗坑：什么是“浅比较”（Shallow Compare）？

`React.memo` 检查 props 是否改变的方法，叫做“浅比较”（其实就是用 `===` 来比较）。

- **对于基本数据类型（数字、字符串、布尔值）：** `1 === 1` (true)，`"你好" === "你好"` (true)。`React.memo` 能完美识别它们没变。
- **对于引用数据类型（对象、数组、函数）：** 还记得我们上个问题聊的吗？在 JavaScript 中，每次定义一个新的对象或函数，它的内存地址都是新的。 `{} === {}` (false) `[] === []` (false) `() => {} === () => {}` (false)

**这就是灾难的开始：**

如果你传给 `React.memo` 子组件的是一个**对象**或**函数**：

```react
const Child = React.memo(({ userInfo, onAction }) => { ... });

function Parent() {
  const [count, setCount] = useState(0);

  // 每次 Parent 渲染，都会生成一个全新的对象（新地址）
  const user = { name: "张三", age: 18 }; 
  
  // 每次 Parent 渲染，都会生成一个全新的函数（新地址）
  const handleClick = () => console.log("点击"); 

  return (
    <>
      <button onClick={() => setCount(count + 1)}>加一</button>
      {/* React.memo 浅比较发现：旧 user !== 新 user，旧函数 !== 新函数 */}
      {/* 结论：拦截失败！子组件依然被重新渲染！ */}
      <Child userInfo={user} onAction={handleClick} />
    </>
  );
}
```



#### 完美闭环：现在你明白 useCallback/useMemo 的作用了吧？

因为 `React.memo` 很“傻”，它只会对比内存地址。

所以，为了救活失效的 `React.memo`，我们必须向 React 求助，把对象的内存地址和函数的内存地址给“缓存（死锁）”下来，别让它们每次渲染都变成新的。

这就是救兵出场的时候：

- **`useMemo`**：用来缓存对象、数组或复杂计算结果，保证它们的内存地址不变。
- **`useCallback`**：用来缓存函数，保证函数的内存地址不变。

**最终形态的优化方案：**

```react
function Parent() {
  const [count, setCount] = useState(0);

  // 用 useMemo 把对象的地址缓存下来
  const user = useMemo(() => {
    return { name: "张三", age: 18 };
  }, []); // 依赖为空，地址永远不变

  // 用 useCallback 把函数的地址缓存下来
  const handleClick = useCallback(() => {
    console.log("点击");
  }, []); // 依赖为空，地址永远不变

  return (
    <>
      <button onClick={() => setCount(count + 1)}>加一</button>
      {/* 现在传进去的永远是同一个内存地址，React.memo 终于能成功拦截了！ */}
      <Child userInfo={user} onAction={handleClick} />
    </>
  );
}
```

### 3. 作为其他 Hook（如 useEffect）的依赖项

如果一个对象、数组或函数必须被作为 `useEffect` 的依赖项，为了防止该引用频繁变化引发无限循环或无谓的副作用执行，应该对其进行缓存。

## 三、何时坚决不用？（反模式 / 过度优化）

很多人习惯性地给所有函数套上 `useCallback`，给所有变量套上 `useMemo`。这不仅不会提升性能，反而会让代码变慢。因为缓存本身是有成本的（需要分配内存、需要每次比对依赖项）。

### 1. 坚决不用：传递给普通的 DOM 元素

原生 DOM 元素（如 `<div>`, `<button>`, `<span>`）不需要、也无法利用引用相等性检查。

**❌ 错误示例：**

```
function SimpleComponent() {
  const [text, setText] = useState("");

  // 毫无意义的 useCallback！
  // <input> 根本不在乎 onChange 是不是同一个引用。
  // 反而每次渲染都要比对依赖项 []，并维护额外的闭包开销。
  const handleChange = useCallback((e) => {
    setText(e.target.value);
  }, []);

  return <input value={text} onChange={handleChange} />;
}
```

### 2. 坚决不用：计算过程非常简单的基本操作

如果只是简单的数组 map、基本数学运算，`useMemo` 的开销往往比计算本身还要大。

### 🚫 什么时候绝对不要用？（负优化灾难区）

**1. 传递给原生的 DOM 元素时（毫无意义）**

```javascript
// ❌ 灾难示范：强行给原生 button 绑定的事件加 useCallback
const handleClick = useCallback(() => {
  console.log("点击了");
}, []);

return <button onClick={handleClick}>提交</button>;
```

原生 DOM 元素（如 `div`, `button`, `input`）根本不在乎你传进来的函数引用是不是变了。就算你每次渲染都给它一个全新的箭头函数，浏览器的渲染引擎也能极快地处理，完全不会触发额外的 DOM 重绘。在这里用 `useCallback`，你纯粹是在白白消耗 React 引擎在底层对比依赖数组（`[]`）的性能。

**2. 极其廉价的简单计算（得不偿失）**

```JavaScript
// ❌ 灾难示范：极其简单的数组衍生
const userNames = useMemo(() => users.map(u => u.name), [users]);
```

对几十条数据的数组做个 `map`，或者做几个数字的加减乘除，JS 引擎执行只需要 0.001 毫秒。但是 `useMemo` 在底层需要分配闭包内存、甚至要去遍历对比 `users` 是否发生了变化，这个“对比成本”往往远大于“计算成本”本身。

### 3. 坚决不用：子组件根本没有用 React.memo 包裹

如果你给子组件传递了一个 `useCallback` 缓存的函数，但该子组件并没有用 `React.memo` 优化，那么只要父组件渲染，子组件依然会 100% 重新渲染。你的缓存毫无意义。

### 4. 坚决不用：依赖项过于频繁地变化

如果你的 `useCallback` 或 `useMemo` 依赖项在几乎每次渲染时都会改变，那么它们不仅每次都在重新创建，还要额外付出“比对依赖项”和“执行 Hook 内部逻辑”的代价，纯粹是负优化。

## 四、总结口诀

- **没有遇到性能瓶颈，就不要用** `useMemo` 和 `useCallback`。
- **计算不贵，别用 `useMemo`**。
- **子组件没用 `React.memo`，别用 `useCallback`**。
- **原生 DOM 标签，完全不需要 `useCallback`**。

> "过早优化是万恶之源"这句话在 React Hooks 开发中体现得淋漓尽致。写出干净、易读的代码才是第一要务。

### 👑 满分面试话术

面对这道题，你可以用下面这段话给出完美的架构师级回答：

“`useMemo` 和 `useCallback` 的本质是**空间换时间**，但很多时候我们忽略了它们自身的执行成本：包括闭包内存的分配、以及依赖数组在每次渲染时的浅比较开销。

因此，我们要遵循‘非必要不缓存’的原则。对于简单的逻辑运算，或者直接传递给原生 DOM 元素的事件函数，绝对不要使用它们，这往往会导致负优化。

它们真正的应用场景只有三个核心地带：

第一，当进行非常耗时的复杂计算时，用 `useMemo` 避免重复执行。

第二，当组件的 Props 需要传递给被 `React.memo` 包裹的、极其沉重的子组件时，必须用 `useCallback` 或 `useMemo` 保证引用的稳定性，否则 `React.memo` 的浅比较会失效，子组件依然会被迫重新渲染。

第三，当引用类型数据（对象/函数）被作为 `useEffect` 等其他 Hook 的依赖项时，需要用它们来保持引用的稳定，防止触发意料之外的无限死循环或重复请求。”
