# 浏览器事件循环如何调度 task、microtask 与渲染？

## 问题

浏览器中的同步代码、`setTimeout`、Promise 回调、`queueMicrotask` 和页面渲染分别如何调度？请解释 task 与 microtask 的执行关系、预测一段代码的输出，并说明它与 Node.js 事件循环有什么不同。

> [!note]- 查看答案
>
> ## 30 秒口述答案
>
> 浏览器事件循环每轮会从某个 task queue 取一个可运行 task 执行；当前 JavaScript 执行栈清空后，会执行 microtask checkpoint，把 microtask queue 一直清空，包括期间新加入的 microtask。Promise reaction 和 `queueMicrotask` 属于 microtask，timer 到期后排入 task。microtask 清空后，浏览器才可能在合适的渲染时机更新页面，但不是每完成一个 task 都一定渲染。规范术语是 task，“宏任务”只是常见教学叫法。Node.js 有 libuv phases 和 `process.nextTick` 等额外规则，不能直接套用浏览器模型。
>
> ## 详细原理
>
> ### 1. ECMAScript 与浏览器宿主各自负责什么
>
> ECMAScript 规范定义执行上下文、Job、Promise reaction 等语言机制，但不会定义 DOM、timer 或浏览器何时绘制。WHATWG HTML Standard 把 ECMAScript 的 Promise jobs 接入浏览器的 microtask queue，并定义 event loop、task queue、timer 和渲染更新等宿主行为。
>
> 因此，“Promise 回调是 microtask”是 Web 宿主整合后的说法；`setTimeout` 也不是 ECMAScript 语法，而是浏览器和 Node.js 分别提供的宿主 API。
>
> ### 2. task 不是单一的全局 FIFO 队列
>
> HTML 规范使用 **task** 与 **task queue**。常说的“宏任务”便于和 microtask 对比，但不是 ECMAScript 或 HTML Standard 的正式术语。
>
> 一个 event loop 可以有多个 task queue。相同 task source 的任务需要维持规范要求的顺序，而浏览器从哪个非空队列选择任务可受实现调度影响。所以不能把所有点击、网络、timer 和消息任务简单画成一个永远严格 FIFO 的“宏任务队列”。
>
> 常见 task 来源包括：
>
> - 初始执行一段 classic script；
> - timer 到期后的回调；
> - 用户交互事件；
> - 消息事件和部分网络事件。
>
> `setTimeout(callback, 0)` 的 `0` 表示最短等待意图，不是立即执行，也不保证精确延迟；只有满足 timer 条件后，回调才有机会作为 task 被调度。
>
> ### 3. microtask checkpoint 会清空队列
>
> Promise 的 `then`、`catch`、`finally` reaction，以及 `queueMicrotask` 注册的回调，会进入 microtask queue。当前 task 的 JavaScript 栈清空后，浏览器在规定的时机执行 microtask checkpoint：按入队顺序不断取出 microtask，直到队列为空。microtask 执行期间新加入的 microtask 也会在本次 checkpoint 中继续执行。
>
> 这解释了两个现象：
>
> 1. 已 fulfilled Promise 的 `then` 仍然晚于当前同步代码执行。
> 1. 持续递归加入 microtask 会长期推迟后续 task 和渲染，造成页面无响应。
>
> ### 4. 渲染是“可能发生”，不是固定插入点
>
> 对 Window event loop 而言，microtask checkpoint 之后，浏览器会在合适的 rendering opportunity 更新渲染；`requestAnimationFrame` 回调属于渲染更新流程，不应简单归为普通 task 或 microtask。浏览器可能因为刷新率、页面是否可见或性能策略跳过某次渲染，所以“每执行一个 task 就一定渲染一次”是错误结论。
>
> 同一个 task 内连续修改 DOM，随后又在 microtask 中修改 DOM，用户通常只会看到 microtask 结束后的最终状态，因为绘制还没有机会发生。若 microtask 过多，也会阻塞绘制。
>
> ### 5. Node.js 不能照搬浏览器结论
>
> Node.js 的事件循环围绕 libuv phases 组织，并且有 `process.nextTick` 等浏览器没有的队列。Node.js 的 timer 阶段细节也可能随 Node/libuv 版本变化。只含标准 Promise 与同步代码的局部推理通常相似，但一旦涉及 `process.nextTick`、`setImmediate`、I/O 或 timer phase，就必须按指定 Node.js 版本和上下文分析。
>
> ## JavaScript 示例
>
> 运行环境：现代浏览器控制台。示例只使用 Web 事件循环语义，不使用 Node.js 专有 API。
>
> ```javascript
> console.log('script start');
>
> setTimeout(() => {
>   console.log('timer');
> }, 0);
>
> Promise.resolve().then(() => {
>   console.log('promise 1');
>   queueMicrotask(() => console.log('nested microtask'));
> });
>
> queueMicrotask(() => {
>   console.log('microtask 1');
> });
>
> console.log('script end');
> ```
>
> 输出：
>
> ```text
> script start
> script end
> promise 1
> microtask 1
> nested microtask
> timer
> ```
>
> 推导过程：
>
> 1. 当前 script 的同步语句先执行，timer 回调等待成为后续 task。
> 1. Promise reaction 先于 `microtask 1` 入队，所以先输出 `promise 1`。
> 1. `promise 1` 中加入的 `nested microtask` 排到已有 `microtask 1` 后面。
> 1. 本轮 microtask queue 清空后，timer task 才有机会执行。
>
> ## 常见追问
>
> 1. **microtask 中继续加入 microtask，会等到下一轮事件循环吗？** 不会；当前 checkpoint 会继续清空队列，因此递归加入可能让 task 和渲染饥饿。
> 1. **`setTimeout(fn, 0)` 为什么不是立即执行？** 它需要先经过 timer 条件，再排入 task queue，并等待当前 task 和随后的 microtask checkpoint 完成；系统调度还可能增加延迟。
> 1. **`requestAnimationFrame` 是“宏任务”吗？** 不宜这样归类。HTML Standard 把 animation frame callbacks 放在更新渲染流程中，它既不是普通 task queue 中的 task，也不是 microtask。
>
> ## 易错点
>
> - 把“宏任务”说成 ECMAScript 的正式术语；规范讨论浏览器调度时使用的是 task。
> - 认为浏览器只有一个严格 FIFO 的 task queue，忽略不同 task source 和实现调度。
> - 认为 microtask checkpoint 只处理检查开始前已有的任务；实际上会持续处理期间新入队的 microtask。
> - 认为 `setTimeout(fn, 0)` 会在 0 毫秒后准时执行，或认为 Promise 回调是同步执行。
> - 固定背诵“每个 task 后必定渲染”，忽略 rendering opportunity 和浏览器调度条件。
> - 用浏览器规则推断 `process.nextTick`、`setImmediate` 或 Node.js I/O 回调顺序。
>
> ## 项目关联
>
> - **已实现：timer 与 Promise continuation 的组合。** `my-ipaas/src/utils/debugSimulator.ts` 的 `waitForStep` 用可注入 timer 创建 Promise；timer 回调调用 `resolve()` 后，`await waitForStep()` 后的模拟执行逻辑会通过 Promise job 继续。默认浏览器 timer 使用 `window.setTimeout`，该模块是前端调试模拟，不是真实集成流执行器。
> - **已实现：timer 防抖。** `my-ipaas/src/stores/flowStore.ts` 在流程树变化后重置 800ms timer，只有一段时间没有新变化才发起保存。800ms 是最短等待目标，不是精确执行时刻。
> - **仅可作为改进练习：自动保存竞态。** 防抖只合并“尚未开始”的保存，不能自动取消或排序已经发出的 PUT。当前实现未见在途保存队列、请求版本或响应过期保护，仍应练习处理旧请求晚完成、覆盖新快照的风险；不得把这项竞态描述成已经解决。
> - **学习边界：** 这些代码可用来画出“timer task -> resolve -> Promise continuation”的时序图，但代码存在不等于小杜已经掌握。
