# 为什么绝不推荐用 `index` 作为 `key`？

在 React 中，`key` 的本质是虚拟 DOM 节点的“唯一身份证”**。而 `index` 只是数据所在的**“相对座位号”。

如果用座位号当身份证，一旦数据发生换座（插入、删除、排序），React 就会发生严重的“认错人”事故。

这不仅是性能问题，更会导致极其致命的**状态串联 Bug**。我们从底层 Diff 机制来拆解这到底是怎么发生的：

### 1. 虚假的更新（引发无用的 DOM 操作）

假设我们有一个数组 `['A', 'B']`，用 `index` 做 key：

- 节点 A 的 key 是 `0`
- 节点 B 的 key 是 `1`

现在，我们在数组**头部**插入一个新元素 `'C'`，数组变成了 `['C', 'A', 'B']`。

此时 React 重新渲染，给它们分配的新 key 是：

- 节点 C 的 key 是 `0`
- 节点 A 的 key 是 `1`
- 节点 B 的 key 是 `2`

**React Diff 算法怎么看？**

React 对比新旧虚拟 DOM，发现 key 为 `0` 的节点还在，只是内容从 `'A'` 变成了 `'C'`。

于是，React **不会**创建一个新的 DOM 节点插在最前面，而是：

1. 把原来 A 的 DOM 强行修改成 C。
2. 把原来 B 的 DOM 强行修改成 A。
3. 在最后新建一个 DOM 节点 B。

原本只需要在头部插入一个新 DOM 的简单操作，变成了全盘的数据覆盖。如果列表有 1000 项，这就是 1000 次 DOM 属性更新，性能极差。

### 2. 致命的状态串联（真实的业务灾难）

性能差还不是最惨的，最惨的是**组件的内部状态（State）会张冠李戴**。

假如我们的列表不仅展示文字，每行还有一个输入框（内部有自己的 `useState` 或原生 DOM 状态）：

1. 你在 `A` 旁边的输入框里写了：“这是 A 的备注”。
2. 然后你在头部插入了 `C`。
3. 由于 React 认为 key 为 `0` 的组件实例没有被销毁，只是 Props 变了，它会**复用**原来的组件实例。
4. **灾难发生：** 你会看到界面上第一行变成了 `C`，但是旁边的输入框里依然填着“这是 A 的备注”！A 的状态被强行绑定到了 C 身上。

如果是删除操作，引发的现象就是：**无论你点击删除哪一项，界面上永远都是最后那一项消失了**，因为 React 发现少了最后一个 index 的 key。

### 标准回答总结（面试直接背诵版）

绝不推荐用 `index` 作为 `key`，主要基于以下两大底层原因：

1. **破坏 Diff 算法，导致性能损耗：** `key` 是 React 识别 VDOM 节点的唯一标识。当数组发生头部插入、删除或排序重组时，`index` 会全部错位。React 会误以为是所有原有组件的 Props 发生了更新，从而引发大量无意义的 DOM 突变（Mutation），而不是高效的节点移动（Move）。
2. **导致组件内部状态错乱（最致命）：** 如果列表项是包含自身状态的有状态组件（或非受控组件如 `<input>`），当 `index` 变化导致身份误判时，React 会错误地复用旧的组件实例。这会导致旧节点的状态（如输入框的内容、Checkbox 的勾选状态）被错误地挂载到新节点上，引发极其严重的业务 Bug。

*(注：只有在列表数据永远不会发生插入、删除、排序的“纯静态展示”场景下，使用 index 作为 key 才是安全的，但为了代码可维护性，依然建议使用唯一的业务 ID。)*
