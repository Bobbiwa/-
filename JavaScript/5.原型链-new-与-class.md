# JavaScript 的原型链、new 和 class 是什么关系？

## 问题

请解释对象的 `[[Prototype]]`、构造函数的 `prototype` 属性、`new` 运算符和 `class` 之间的关系。为什么说 `class` 基于原型机制，但不能简单断言它“只是语法糖”？

> [!note]- 查看答案
>
> ## 30 秒口述答案
>
> 每个普通对象都有一个内部 `[[Prototype]]`，属性查找会从对象自身沿这条链一直查到 `null`。构造函数的公开 `prototype` 属性是另一个对象；执行 `new F()` 时，新实例的 `[[Prototype]]` 通常会指向 `F.prototype`，所以实例能共享其中的方法。`class` 的实例方法同样放在 `Class.prototype` 上，`extends` 也会建立原型关系，因此它基于原型模型。但类构造器必须用 `new`、类体默认严格模式、方法默认不可枚举，并且还有 `super`、私有字段等额外语义，所以不能把它粗暴等同于普通构造函数的纯语法替换。
>
> ## 详细原理
>
> ### `[[Prototype]]` 不等于 `.prototype`
>
> - `[[Prototype]]` 是对象的内部槽，值为另一个对象或 `null`。可以用 `Object.getPrototypeOf(obj)` 读取，用 `Object.create(proto)` 在创建对象时指定。
> - 可构造的普通函数通常具有自有的 `.prototype` 普通公开属性；箭头函数、对象方法和绑定函数等并不因此自动拥有该属性。构造函数的 `.prototype` 通常参与决定新实例的 `[[Prototype]]`。
> - 当 `F` 使用普通构造流程、`F.prototype` 是对象且构造函数没有返回替代对象时，典型关系是 `Object.getPrototypeOf(new F()) === F.prototype`，而不是“实例拥有一个等于构造函数的 `prototype` 属性”。
> - `__proto__` 是用于访问原型的历史兼容访问器，不应把它当成规范内部槽本身。新代码优先使用 `Object.getPrototypeOf`、`Object.create`；也应避免在热路径中动态调用 `Object.setPrototypeOf`，因为改变既有对象的原型可能破坏引擎优化。
>
> 当读取 `obj.key` 时，普通对象先检查自己的属性；若没有，再对其 `[[Prototype]]` 重复相同查找，直到找到属性或原型为 `null`。因此：
>
> - `Object.hasOwn(obj, key)` 只判断自有属性；`key in obj` 会包含原型链上的属性。
> - 给实例赋值通常会创建或更新自有属性，遮蔽原型上的同名属性，而不是直接修改原型属性。
> - 多个实例可以通过共同的原型共享方法，避免每次构造都创建一份同功能函数。
>
> ### `new` 触发构造语义
>
> `new F(...args)` 并不只是手写几行对象操作，它会检查目标是否具有 `[[Construct]]`，并调用规范的构造流程。对常见的普通基类构造函数，可以用下面的近似步骤理解：
>
> 1. 创建一个新对象。若 `F.prototype` 是对象，就将其作为新对象的 `[[Prototype]]`；否则回退到对应 realm 的 `%Object.prototype%`。
> 1. 以新对象作为构造期间的 `this`，传入参数执行 `F`。
> 1. 如果 `F` 显式返回一个对象，则 `new` 表达式采用该对象；如果返回原始值或没有显式返回，则采用最初创建的新对象。
>
> 这是帮助理解普通构造函数的模型，不是对所有构造器的等价实现。内置构造器、Proxy 和派生类都有额外的内部语义；派生类构造器必须先调用 `super()` 才能访问 `this`，因为实例由父类构造流程创建并初始化。
>
> `F.prototype` 被替换后，只影响之后以它为原型创建的实例；旧实例仍指向原来的原型对象。反过来，若只是修改原有 `F.prototype` 对象上的属性，已经存在的实例也可能通过原型链看到变化。
>
> ### `class` 建立在原型模型之上
>
> ```javascript
> class Parent {
>   speak() {
>     return 'parent';
>   }
> }
>
> class Child extends Parent {}
> ```
>
> 上例会建立两条相关但不同的继承链：
>
> - 实例方法链：`Object.getPrototypeOf(Child.prototype) === Parent.prototype`。
> - 构造器静态成员链：`Object.getPrototypeOf(Child) === Parent`。
>
> `Child` 的实例以 `Child.prototype` 为直接原型，并继续沿链访问 `Parent.prototype` 上的 `speak`。普通实例方法定义在 `.prototype` 上，静态方法定义在类构造器本身；实例字段则在构造期间初始化到每个实例上。
>
> 因此，说 `class` **基于原型和构造机制提供了更高层语法**是准确的；说它“只是语法糖、与普通构造函数完全一样”则会遗漏可观察差异：
>
> - 类构造器不带 `new` 调用会抛出 `TypeError`。
> - 类体始终使用严格模式。
> - 类声明的绑定具有类似暂时性死区的限制，不能像函数声明那样在初始化前调用。
> - 类语法定义的原型方法默认不可枚举，而直接赋值 `F.prototype.method = ...` 创建的属性默认可枚举。
> - 派生构造器受 `super()` 和 `this` 初始化规则约束。
> - 私有字段使用私有名称和品牌检查，不是原型链上的普通字符串属性，不能用简单的构造函数赋值完整模拟其语义。
>
> ### `instanceof` 不是类型的绝对证明
>
> 当右侧是普通非绑定构造函数且未自定义 `Symbol.hasInstance` 时，`value instanceof F` 会检查 `F.prototype` 是否出现在 `value` 的原型链中。绑定函数会把默认判断委托给它的目标函数，其他对象也可以通过 `Symbol.hasInstance` 自定义行为。不同 realm（例如不同 iframe）拥有各自的内建构造器和原型对象，所以跨 realm 的数组可能不满足当前 realm 的 `Array` 的 `instanceof`；这类判断应优先考虑 `Array.isArray` 等专用 API。
>
> ## JavaScript 示例（Node.js 23 或现代浏览器）
>
> ```javascript
> class Base {
>   speak() {
>     return this.name;
>   }
> }
>
> class User extends Base {
>   constructor(name) {
>     super();
>     this.name = name;
>   }
> }
>
> const user = new User('小杜');
>
> console.log(Object.getPrototypeOf(user) === User.prototype); // true
> console.log(Object.getPrototypeOf(User.prototype) === Base.prototype); // true
> console.log(Object.getPrototypeOf(User) === Base); // true
> console.log(Object.prototype.hasOwnProperty.call(user, 'name')); // true
> console.log(Object.prototype.hasOwnProperty.call(user, 'speak')); // false
> console.log(user.speak()); // 小杜：从 Base.prototype 找到方法
> console.log(Object.keys(Base.prototype)); // []：class 方法默认不可枚举
>
> function ReturnsObject() {
>   this.created = true;
>   return { replacement: true };
> }
>
> function ReturnsPrimitive() {
>   this.created = true;
>   return 1;
> }
>
> console.log(new ReturnsObject()); // { replacement: true }
> console.log(new ReturnsPrimitive()); // ReturnsPrimitive { created: true }
> ```
>
> 最后一行的对象展示格式可能因控制台不同而不同，但它的 `created` 属性为 `true`，且原型是 `ReturnsPrimitive.prototype`。
>
> ## 常见追问
>
> 1. **替换 `Constructor.prototype` 后，已有实例会怎样？** 已有实例仍指向旧原型对象；新实例通常指向新原型。若只修改原原型对象的属性，已有实例仍能沿原型链观察到修改。
> 1. **`Object.create(proto)` 与 `new Constructor()` 有什么区别？** 前者直接创建以 `proto` 为原型的对象，不执行构造函数；后者执行目标的 `[[Construct]]` 流程，包含参数传递、初始化和构造函数返回值规则。
> 1. **实例方法、静态方法和实例字段分别放在哪里？** 普通实例方法在 `Class.prototype` 上，静态方法在类构造器对象上，实例字段在每个实例自身；私有字段还有独立的私有名称与品牌检查语义。
>
> ## 易错点
>
> - 混淆实例的 `[[Prototype]]` 和构造函数的 `.prototype`，或认为实例直接拥有构造函数的 `prototype` 属性。
> - 手写 `new` 时忘记：目标必须可构造、`prototype` 非对象时需要回退，以及构造函数显式返回对象会替换默认实例。
> - 认为箭头函数可以作为构造器。箭头函数没有 `[[Construct]]`，也通常没有用于构造实例的自有 `prototype` 属性。
> - 把 `class` 粗暴描述成“纯语法糖”，忽略严格模式、不可直接调用、方法可枚举性、`super` 和私有字段等可观察语义。
> - 认为 `instanceof` 检查的是不可变的“类型标签”，忽略原型可变、`Symbol.hasInstance` 和跨 realm 场景。
> - 为了继承在运行时频繁修改对象原型；这既难以维护，也可能影响引擎优化。
>

### 1. new关键字到底做了什么？

当在 JavaScript 中使用 `new` 关键字调用构造函数时，JavaScript 引擎在底层严格按照以下四个明确的技术步骤执行：

1. 创建新对象 (Create a new object)

在内存中创建一个全新的、空的普通 JavaScript 对象（即 `{}`）。

2. 链接原型 (Link the prototype)

将这个新对象的内部槽 `[[Prototype]]`（可通过 `__proto__` 或 `Object.getPrototypeOf` 访问）指向并链接到构造函数的 `.prototype` 属性对象上。 *技术目的：建立原型链查找机制，使实例对象能够继承并访问构造函数原型上定义的公共方法和属性。*

3. 绑定 `this` 并执行构造函数 (Bind `this` and execute)

将构造函数的执行上下文（`this`）显式绑定到第一步创建的这个新对象上，将传入的参数传递给构造函数，并执行函数体内的代码。 *技术目的：通过执行形如 `this.property = value` 的赋值逻辑，为新对象初始化其自身的实例属性。*

4. 处理返回值 (Handle the return value)

引擎会检查构造函数执行完毕后的实际返回值，以决定最终对外输出的对象：

- **若返回引用类型：** 如果构造函数显式返回了一个非 `null` 的对象（包括普通对象、数组、函数等），则 `new` 表达式直接返回该对象（第一步创建的对象会被丢弃并等待垃圾回收）。
- **若返回基本类型：** 如果构造函数没有返回值（默认返回 `undefined`），或者显式返回了基本数据类型（如字符串、数字、布尔值、`null`），引擎会忽略这个返回值，`new` 表达式最终返回的是在第一步创建并已初始化完毕的那个新对象。

### 面试实战：手写一个 `new` 函数

```javascript
/**
 * 模拟 new 关键字的函数
 * @param {Function} constructor - 构造函数 (比如 Person)
 * @param {...any} args - 传给构造函数的参数 (比如 '小杜', 25)
 */
function myNew(constructor, ...args) {
  
  // 【第 1 步】和【第 2 步】合并：
  // Object.create(proto) 会创建一个空对象，并且直接把它的原型指向 proto
  const obj = Object.create(constructor.prototype);

  // 【第 3 步】：调用构造函数，把 this 强行绑定到新对象 obj 上，并把参数传进去
  // 用 apply 或者 call 都可以
  const result = constructor.apply(obj, args);

  // 【第 4 步】：检查返回值
  // 判断 result 是否为对象（且不能是 null，因为 typeof null 也是 'object'）或者函数
  if (result !== null && (typeof result === 'object' || typeof result === 'function')) {
    return result; // 如果构造函数执意要返回自己的对象，就顺从它
  }
  
  return obj; // 否则，把咱们刚装修好的 obj 交出去
}
```

测试一下我们手写的 `myNew`

```javascript
function Person(name, age) {
  this.name = name;
  this.age = age;
}
Person.prototype.sayHi = function() {
  console.log('Hi, 我是 ' + this.name);
}

// 原生的 new
const p1 = new Person('原生小杜', 18);
p1.sayHi(); // Hi, 我是 原生小杜

// 我们手写的 myNew
const p2 = myNew(Person, '手写小杜', 20);
p2.sayHi(); // Hi, 我是 手写小杜

console.log(p2.__proto__ === Person.prototype); // true (认祖归宗成功)
```



### 2. 构造函数的返回与不返回

在普通函数中，如果没有 `return`，默认返回 `undefined`。但在配合 `new` 关键字使用时，JavaScript 引擎定下了一条特殊的**强制拦截规则**。

当 `new` 走到最后一步“交钥匙”时，它会检查你 `return` 的到底是什么东西，分为两种情况：

**情况 A：返回的是“基本数据类型”（或者不写 return）**

如果构造函数返回的是字符串、数字、布尔值、`null` 或 `undefined`，**引擎会直接无视你的 `return`**，强行把刚建好的那个实例对象（`this`）交出去。

```javascript
function PersonA(name) {
  this.name = name;
  return "我是来捣乱的字符串"; // 引擎：基本类型？直接无视！
}

const a = new PersonA("小杜");
console.log(a); // 依然完美输出：PersonA { name: "小杜" }
```

**情况 B：返回的是“引用数据类型”（对象、数组、函数等）**

如果你在构造函数里强行返回了一个**新的对象**，引擎就会认为：“看来你不想用我帮你建的那个 `this`，你想自己造个新房子。” 于是，引擎会**直接丢弃掉 `this`，把你返回的新对象交出去**。

```javascript
function PersonB(name) {
  this.name = name; // 这个 this 最终会被无情丢弃
  return { message: "你的实例被我狸猫换太子了！" }; 
}

const b = new PersonB("小杜");
console.log(b); // 输出：{ message: "你的实例被我狸猫换太子了！" }
console.log(b.name); // 输出：undefined (因为拿到的根本不是 this)
```

> **核心记忆点：** `new` 遇到 `return`，如果是基本类型就**无视**，如果是对象就**替换**。



### 3. class 与 构造函数的恩怨情仇（真的是语法糖吗？）

很多人只知道 `class` 的底层是构造函数，但它们在实际运行中，有着非常严格的区别。设计 `class` 的目的，就是为了填补老式构造函数的那些“反直觉漏洞”。

### ES6 Class vs ES5 Constructor

ES6 Class Syntax

```javascript
class User {
  constructor(name) {
    this.name = name;
  }

  sayHi() {
    console.log(this.name);
  }
}

// Requirement: Must use 'new'
const u = new User('Alice');
```

ES5 Constructor Function

```javascript
function User(name) {
  this.name = name;
}

User.prototype.sayHi = function() {
  console.log(this.name);
};

// Can be invoked without 'new'
const u = User('Alice');
```

### 核心区别对照表

| **维度**                | **老式构造函数 (function F())**                              | **ES6 现代类 (class C {})**                                  |
| ----------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **忘记写 `new` 调用时** | 💥 **灾难：** 变成普通函数，`this` 泄漏到全局（修改 `window`），不报错。 | 🛡️ **安全：** 直接抛出 `TypeError`，强制你必须用 `new` 调用。 |
| **严格模式**            | 默认是非严格模式，除非手动写 `'use strict'`。                | 强制全局和内部全部使用**严格模式**，无法关闭。               |
| **方法的可见性 (枚举)** | `F.prototype` 上的方法默认是可以被 `for...in` 遍历到的。     | `class` 内部定义的所有方法，默认**不可枚举**（更像内置对象的行为）。<br />意义：当我们使用 `for...in` 循环去遍历一个对象时，我们通常只想看到这个对象的**数据（属性）**，而不是它能做什么**动作（你绝对不想把 `push`、`pop`、`slice` 这些内置方法也遍历出来）**。 |
| **变量提升 (Hoisting)** | 存在完整的变量提升，可以在声明之前实例化对象。               | 存在提升，但有**暂时性死区 (TDZ)**，声明前调用直接报错。     |
| **静态方法的继承**      | 子类**不会**自动继承父类的静态方法（需手动 `Object.setPrototypeOf`）。<br />细节如下补充 | `extends` 会自动让子类继承父类的静态方法。                   |

**老式构造函数实现继承方式：**

**方式一：标准现代 API（推荐）** 使用 `Object.setPrototypeOf()` 直接修改原型的指向。这也是 Bable 编译器把 `class` 转换成 ES5 时最常用的底层代码。

JavaScript

```
function Parent() {}
Parent.sayHello = function() { console.log("我是父类的静态方法"); };

function Child() {}

// 让 Child 继承 Parent 的静态方法
Object.setPrototypeOf(Child, Parent); 

Child.sayHello(); // 输出: "我是父类的静态方法"
```

**方式二：历史遗留属性（不推荐，但要知道）** 直接修改 `__proto__` 属性。

JavaScript

```
// 作用和上面完全一样，但在生产环境中不推荐直接操作 __proto__
Child.__proto__ = Parent; 
```

**方式三：暴力拷贝（老旧库的兼容做法）** 如果环境连 `Object.setPrototypeOf` 都不支持（极低版本的浏览器），就只能用 `for...in` 把父类身上的属性硬拷过去。

JavaScript

```
for (var key in Parent) {
  if (Parent.hasOwnProperty(key)) {
    Child[key] = Parent[key];
  }
}
```

### 总结：为什么说它不只是语法糖？

如果 `class` 仅仅是语法糖，那把 `class` 代码转换成老式的 `function` 代码后，它们的行为应该是一模一样的。

但正如上面的表格所示，`class` 强加了**安全限制（必须用 new）**、**环境限制（严格模式）\**和\**属性描述符限制（不可枚举）**。这些都是你用老式构造函数极难完美模拟的。

所以面试时最准确的说法是：**“`class` 确实建立在原型链机制之上，但它不仅仅是语法糖，它是一种带有更严格语义和安全机制的全新语法结构。”**bia



### 4.在 ES6 的 class 继承中，子类的 constructor 里必须先调用 super() 才能使用 this，这是为什么？底层到底发生了什么？

在面试中，如果你只回答“因为规范就是这么写的”，那就太可惜了。ES6 这样设计，是因为它在底层对“谁来创建对象”这个问题，进行了一次**彻底的权力反转**。

我们用“建房子”的比喻，把 ES5 和 ES6 继承的底层逻辑撕开来看：

**1. 旧时代 (ES5)：子类造房子，请父类来装修**

在 ES5 中，对象的创建权掌握在**子类**手里。

当执行 `new Child()` 时：

1. 引擎会先在 `Child` 内部凭空造出一个全新的 `this`（建好房子的毛坯）。
2. 然后我们通过 `Parent.call(this)`，把这个房子交给父类，让父类在里面添置家具（挂载属性）。
3. 父类装修完后，子类再继续往 `this` 上加自己的专属家具。

JavaScript

```
// ES5 继承机制
function Parent(name) {
  this.name = name; // 2. 父类收到 this，挂载 name
}

function Child(name, age) {
  // 1. 引擎在此刻已经造好了 this
  Parent.call(this, name); // 2. 把 this 传给父类去装修
  this.age = age; // 3. 子类继续操作 this
}
```

**2. 新时代 (ES6)：父类造房子，交给子类去装修**

ES6 彻底颠覆了这个过程，对象的创建权被上交给了**父类**。

在 `class Child extends Parent` 中，当执行 `new Child()` 时：

1. **子类根本没有资格创建 `this`。** 引擎处于“挂起”状态。
2. 你**必须**调用 `super()`，这相当于给父类打电话：“爸，你帮我把房子（this）建好”。
3. **底层发生的事情：** 引擎跳转到 `Parent` 的 constructor，由父类按照它的底层规则，开辟内存，建好房子，并挂载好父类的属性。
4. 父类把建好、装修了一半的房子（`this`）**返回并移交**给子类。
5. 此时，子类终于拿到了 `this`，可以继续往上面加自己的属性了。

这也就是为什么：**在调用 `super()` 之前，子类里根本就不存在 `this`**。如果你强行访问 `this`，引擎就会直接抛出 `ReferenceError`。

JavaScript

```
// ES6 继承机制
class Child extends Parent {
  constructor(name, age) {
    // console.log(this); // ❌ 报错！此时房子还没建好，不存在 this
    
    super(name); // ✅ 呼叫父类去建房子，并返回 this 给子类
    
    // 此时才有了 this
    this.age = age; 
  }
}
```

**3. 核心大揭秘：当年为什么要搞这种“权力反转”？**

你可能会问：“ES5 的方式不是挺好理解的吗？为什么要多此一举搞反转？”

**根本原因是：为了让 JavaScript 能够真正继承原生对象（比如 `Array`、`Error`、`Map` 等）。**

在 ES5 时代，我们**永远无法完美继承**一个 `Array`：

JavaScript

```
// ES5 试图继承数组
function MyArray() {
  Array.call(this); // 试图把普通对象变成数组
}
const arr = new MyArray();
arr[0] = "hello";
console.log(arr.length); // 输出 0！继承失败！
```

**为什么失败？** 因为原生数组的 `length` 自动更新等“超能力”，是直接写死在 C++ 底层引擎里的（内部槽）。通过 `Array.call(this)`，父类 `Array` 面对子类传过来的普通毛坯房，根本无法把它强行改造成具有底层超能力的数组。这种超能力**必须在开辟内存的第一步由原生构造函数自己创建**。

**ES6 完美解决了这个问题：** 既然必须由父类亲自建房才有超能力，那就让父类去建！ 当你 `class MyArray extends Array` 并调用 `super()` 时，是底层的 `Array` 亲自出马，建好了一个拥有所有底层超能力的真正数组对象，然后把它移交给 `MyArray`。从此，JavaScript 终于迎来了真正的内置对象子类化。



### 5.class A extends B 底层到底做了什么？

在面试中，如果面试官问：“`class A extends B` 底层到底做了什么？”

90% 的人只能答出：“让 A 的实例能继承 B 的方法。”

而你要给出那剩下的 10% 的满分答案：**“`extends` 在底层同时悄悄建立了两条不同的原型链连接，一条为了实例，一条为了类本身。”**

我们把这“两条链”扒开来看个清清楚楚：

**第一条链：实例方法链（传承给下一代的技能库）**

这是大家都熟悉的一条链。它的目的是让 `Child` 造出来的孩子，能顺着原型链借用 `Parent` 基因库里的方法。

- **底层动作：** 引擎强行修改了 `Child.prototype` 这个对象的隐式原型（`[[Prototype]]`），让它指向 `Parent.prototype`。

- **等价的底层代码：**

  JavaScript

  ```
  // 用 Object.create 换掉原有的 Child.prototype，并指明它的“干爹”是谁
  Child.prototype = Object.create(Parent.prototype);
  // 别忘了把 constructor 指回自己
  Child.prototype.constructor = Child; 
  ```

- **寻宝路径：**

  当执行 `const c = new Child(); c.speak();` 时：

  1. 找 `c` 自己身上有没有 `speak`？没有。
  2. 顺着 `c.__proto__` 找到 `Child.prototype`（没找到）。
  3. **关键连接点：** 顺着 `Child.prototype.__proto__` 继续往上找，来到了 `Parent.prototype`，找到了 `speak` 方法，执行！

**第二条链：类本身的静态链（继承上一代的家族企业）**

这是 ES5 时代的老旧写法（`Parent.call(this)`）很难自动做到，而 ES6 `extends` 帮你完美解决的痛点。

除了给孩子用的方法，如果父类自己身上有静态方法（`static fn() {}`），子类该怎么继承？

- **底层动作：** 引擎直接修改了 `Child` 这个构造函数（或者说类本身）的隐式原型，让它指向 `Parent` 这个构造函数。

- **等价的底层代码：**

  JavaScript

  ```
  Object.setPrototypeOf(Child, Parent);
  ```

- **寻宝路径：**

  当执行 `Child.staticMethod()` 时：

  1. 找 `Child` 这个函数对象自己身上有没有 `staticMethod`？没有。
  2. **关键连接点：** 顺着 `Child.__proto__` 往上找，来到了 `Parent` 这个函数对象身上，找到了静态方法，执行！

**总结：`extends` 的底层公式**

如果我们在底层用手写代码来模拟 `class Child extends Parent`，核心逻辑就是这两句话：

JavaScript

```
// 【连接第一条链：为了实例方法】
// 让 Child.prototype.__proto__ === Parent.prototype
Object.setPrototypeOf(Child.prototype, Parent.prototype); 

// 【连接第二条链：为了静态方法】
// 让 Child.__proto__ === Parent
Object.setPrototypeOf(Child, Parent); 
```

**为什么说这是极为精妙的设计？**

在 JavaScript 里，**万物皆对象**。

不仅你 `new` 出来的实例是对象，**类（构造函数）本身也是一个对象**。

`extends` 关键字的精妙之处就在于，它敏锐地意识到了这一点，并同时处理了这两个“对象”的继承关系：

1. 它把两个类的**原型对象**（`.prototype`）连起来了，处理了**实例**的继承。
2. 它把两个**类本身**连起来了，处理了**静态方法**的继承。

这也就是为什么你能写出 `Child.prototype.__proto__ === Parent.prototype` 和 `Child.__proto__ === Parent` 这两个双重成立的等式。



### 6. 既然在 ES6 中 this 是由父类创建的，那父类怎么知道要把这个新对象的隐式原型指向子类呢？这里面是不是用到了 ES6 的新特性 new.target？

**你简直太敏锐了！完全命中靶心！** 🎯

这就是 ES6 继承机制中最核心、最隐秘的魔法：**`new.target`**。

在 ES6 之前，JavaScript 引擎确实无法知道“真正发起调用的到底是谁”。为了解决这个“身份丢失”的问题，ES6 专门引入了一个元属性（Meta Property）—— `new.target`。

我们用一句话来概括它的作用：

**`new.target` 永远指向那个“最开始被 `new` 关键字直接调用的类（或构造函数）”。**

我们通过三个步骤，彻底把这个底层机制剥开：

**1. 隐蔽的“身份传递”**

当你执行 `new Child()` 的时候，引擎在底层悄悄开启了一场“击鼓传花”的游戏：

1. **起点：** 你写了 `new Child()`。引擎立刻做了一个标记：`new.target = Child`。
2. **呼叫父类：** `Child` 的 `constructor` 执行到 `super()`。
3. **关键传递：** `super()` 并不是简单地调用 `Parent`，它在底层相当于 `Reflect.construct(Parent, args, new.target)`。也就是说，**它把 `Child` 的身份牌作为隐藏参数，递给了 `Parent`。**

**2. 父类如何“看牌造房”？**

当执行流来到父类 `Parent` 的 `constructor` 时，父类要开始开辟内存建房子（造对象）了。

父类在底层做了这样一次判断：

- “我看看传过来的 `new.target` 是谁？哦，原来是 `Child`。”
- “好，我开辟一块新内存，并且我得用 `Child.prototype` 作为这块内存的基因库（隐式原型）。”

这就完美解释了，为什么明明是父类造的对象，最后交回到子类手里时，对象的 `__proto__` 却精准地指向了 `Child.prototype`。

**3. 用代码“抓个现行”**

我们可以用一段极其简单的代码，把这个引擎底层的“秘密交易”直接打印出来，你看一眼就全明白了：

```javascript
class Parent {
  constructor() {
    // 父类通过打印 new.target，偷看了一眼“到底是谁在请我出山”
    console.log("当前造房子的真正雇主 (new.target) 是：", new.target.name);
    
    // 父类也可以直接看看，自己造出来的 this，到底连着谁的原型
    console.log("刚造好的 this 的原型是不是 Child？", Object.getPrototypeOf(this) === Child.prototype);
  }
}

class Child extends Parent {
  constructor() {
    super(); 
  }
}

// ============== 测试开始 ==============

console.log("--- 直接 new 父类 ---");
new Parent(); 
// 输出: 
// 当前造房子的真正雇主 (new.target) 是： Parent
// (此时 this 的原型是 Parent.prototype)

console.log("\n--- new 子类 ---");
new Child(); 
// 输出: 
// 当前造房子的真正雇主 (new.target) 是： Child
// 刚造好的 this 的原型是不是 Child？ true
```

**总结：为什么说这是一个伟大的设计？**

如果没有 `new.target`，父类造对象时就只能死板地用自己的 `Parent.prototype`。这样造出来的对象，子类拿到手后，还得用极度消耗性能的手段（比如 `Object.setPrototypeOf`）去强行修改原型链。

有了 `new.target`，引擎在分配内存的**那一瞬间（第一步）**，就直接把原型链一步到位地连到了子类上。不仅性能极高，而且让内置对象（如 `Array`）的继承成为了可能。
