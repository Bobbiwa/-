# 什么是闭包？它与词法作用域有什么关系？

## 问题

什么是 JavaScript 闭包？它为什么能在外层函数返回后继续访问外层变量？闭包捕获的是变量当时的值还是绑定？请说明它在异步回调、循环和资源清理中的常见应用与风险。

> [!note]- 查看答案
>
> ## 30 秒口述答案
>
> 闭包可以理解为函数和它定义时可访问的词法环境的组合。JavaScript 是词法作用域，名字解析取决于函数写在哪里，而不是从哪里调用。只要内部函数仍可达，它需要的外层绑定就可以继续存活，所以外层函数返回后仍能读取或修改这些绑定。闭包通常捕获的是绑定，不是自动冻结的值，因此之后对绑定的修改会被回调看到。它常用于私有状态、回调和异步控制；闭包本身不是内存泄漏，只有无用闭包长期可达并保留大对象或资源时才形成问题。
>
> ## 详细原理
>
> ### 1. 词法作用域决定查找路径
>
> 词法作用域由源码嵌套结构决定。函数体访问一个局部没有声明的名字时，会沿定义位置对应的外层 Environment Record 查找，而不会改用调用者的局部作用域。
>
> ECMAScript 普通函数对象带有内部槽 `[[Environment]]`，记录函数创建时关联的外层环境。调用函数时又会建立本次调用的函数 Environment Record，并以保存的外层环境连接作用域链。日常所说的“闭包”就是这一语言机制表现出的能力；它不是手动复制一张变量表。
>
> ### 2. 为什么外层函数返回后变量还能存在
>
> 外层函数调用结束意味着它的执行上下文退出调用栈，不等于其全部环境立即销毁。如果返回的函数、定时器回调、Promise 回调或事件监听器仍可达，并且需要该环境，相关绑定就必须保留。等这些函数和环境不再可达后，垃圾回收器才有机会回收它们；具体回收时机属于实现细节，代码不能依赖某个确定时刻。
>
> 每次调用外层函数通常会建立独立的函数环境，所以工厂函数创建出的多个计数器可以拥有互不干扰的状态。
>
> ### 3. 捕获绑定，不是自动保存快照
>
> 闭包通常读取的是词法环境中的绑定。外层代码后来给同一绑定重新赋值，闭包再次执行时会看到新值。若业务需要创建当时的快照，应在当次作用域中建立不会再改绑的局部绑定，或显式复制所需数据；对象快照还要考虑浅拷贝与深拷贝语义。
>
> 经典循环问题也来自绑定是否共享：`var` 循环中的多个回调通常共享同一个函数级绑定；`for` 头部的 `let` 会为各次迭代建立对应绑定，所以回调得到 `0、1、2`。
>
> ### 4. 常见用途与生命周期风险
>
> - **封装状态：** 工厂函数返回操作函数，外部只能通过规定接口访问内部状态。
> - **异步控制：** Promise、timer 或 React Effect 的回调共享某次操作的状态，例如请求是否已失效。
> - **函数配置：** 柯里化、偏函数和事件处理器可保留创建时的配置。
> - **防抖与节流：** 多次调用共享 timer binding，以取消或复用之前的调度。
>
> 闭包不会天然造成内存泄漏。真正的风险是本应失效的 timer、事件监听器、订阅或缓存仍然可达，使闭包连带保留大对象。应在生命周期结束时清理外部注册，并避免无意捕获整个大对象。现代引擎可以优化环境保存方式，但这属于实现策略，面试时不应承诺某个变量一定如何分配或回收。
>
> ## JavaScript 示例（Node.js 23）
>
> ```javascript
> "use strict";
>
> function createCounter(initialValue) {
>   let count = initialValue;
>
>   return {
>     increment() {
>       count += 1;
>       return count;
>     },
>     read() {
>       return count;
>     },
>   };
> }
>
> const first = createCounter(0);
> const second = createCounter(10);
> console.log(first.increment()); // 1
> console.log(first.read()); // 1
> console.log(second.read()); // 10：来自另一次调用的独立环境
>
> let current = "before";
> const readCurrent = () => current;
> current = "after";
> console.log(readCurrent()); // after：读取同一个绑定，不是创建函数时的字符串快照
>
> const delay = (milliseconds) => new Promise((resolve) => {
>   setTimeout(resolve, milliseconds);
> });
>
> function startJob() {
>   let cancelled = false;
>
>   const done = (async () => {
>     await delay(0);
>     return cancelled ? "cancelled" : "completed";
>   })();
>
>   return {
>     cancel() {
>       cancelled = true;
>     },
>     done,
>   };
> }
>
> (async () => {
>   const job = startJob();
>   job.cancel();
>   console.log(await job.done); // cancelled
> })();
> ```
>
> 这个异步示例中的 `cancel` 只改变共享状态，并没有取消底层 timer。真实业务若要释放资源，还需要相应的 `clearTimeout`、`AbortController`、取消订阅或移除监听器。
>
> ## 常见追问
>
> 1. **闭包捕获的是值还是变量？** 更准确地说，它通过词法环境访问绑定。绑定后来重新赋值时，闭包通常会读到新值；需要快照时要另建绑定或显式复制数据。
> 1. **闭包为什么可能与内存泄漏有关？** 只要闭包仍可达，它依赖的环境也可能被保留。泄漏的根因通常是忘记清理监听器、timer、订阅或无限增长的缓存，而不是“用了闭包”本身。
> 1. **`var` 和 `let` 为什么让循环回调得到不同结果？** 多个 `var` 回调共享同一函数级绑定，循环结束时它已是最终值；`for` 中的 `let` 会为各次迭代建立对应绑定。
>
> ## 易错点
>
> - 认为只有“外层函数返回内部函数”才算闭包；事件处理器、Promise 回调等同样可以闭合外层环境。
> - 认为闭包保存了创建瞬间所有变量的值；它通常关联的是绑定，且不相关变量是否被优化属于实现细节。
> - 把“执行上下文出栈”误解成外层环境必定立即销毁，忽略可达闭包仍需该环境。
> - 笼统地说“闭包一定内存泄漏”，没有说明可达性和资源生命周期。
> - 用布尔 `cancelled` 阻止后续状态写入后，就宣称底层请求或 timer 已被取消。
>

### 1. 闭包到底是个什么？它是 Hack 技巧吗？

**明确结论：闭包绝不是 Hack 编码技巧，它是 JavaScript（以及所有支持函数式编程语言）最核心、最正统的设计机制。**

很多初学者觉得闭包像个“黑魔法”或 Hack，是因为在像 C 或早期的 C++ 这样的语言中，函数执行完毕后，内部的局部变量会立刻随着调用栈（Stack）的销毁而灰飞烟灭。如果你试图返回一个指向这些局部变量的指针，程序直接就会崩溃（段错误）。

但在 JavaScript 中，函数是“一等公民”，这意味着函数可以像普通数据一样被传来传去（作为参数传递，或者作为返回值返回）。

试想一下，如果 JavaScript 允许你把一个内部函数 `return` 到外部去用，但同时又无情地把这个内部函数所依赖的外层变量全部销毁，那这个内部函数不就成了一个“废人”吗？

为了解决这个问题，JavaScript 引擎在底层做了精心设计：

当它发现一个内部函数被暴露出去了，并且它还在引用着外层函数的变量时，引擎会把这些变量从原本的“执行栈（Stack）”中转移到“堆内存（Heap）”中专门保护起来，和这个内部函数打包在一起。

这个“函数 + 它被保护起来的周边变量环境”的包裹，就是闭包。

所以，闭包不是开发者钻了语言的空子，而是语言的创造者为了让“函数可以作为返回值到处跑”而必须配套提供的基础设施。

### 2. 词法作用域到底指什么？你的理解对吗？

**明确结论：你的理解不仅完全正确，而且一针见血！**

你说的非常对：**变量名的查找，完全由函数定义时“写”在代码里的位置决定，绝对不看它是在哪里被“调用”的。**

那为什么叫“词法（Lexical）”呢？

这个词源自编译原理中的“词法分析（Lexical Analysis）”**。在代码被运行之前，编译器首先要把你写的源代码当成纯文本进行扫描解析。 因为这种作用域完全是根据你**写代码时的物理文本结构（嵌套关系）在编译阶段就已经确定的，所以它被称为“词法作用域”（也叫静态作用域）。

我们可以用一段极其简单的代码来印证你的理解：

JavaScript

```
let value = "全局的值";

function printValue() {
  // 这个函数在定义时，它外层的作用域里只有全局的 value
  console.log(value); 
}

function callPrint() {
  let value = "callPrint 内部的值"; // 这里有一个局部同名变量
  
  // 虽然在这里调用，但 printValue 根本不管这里有什么
  printValue(); 
}

callPrint(); 
// 输出结果是什么？
// 答案是："全局的值"
```

如果 JavaScript 采用的是调用位置决定的作用域（那叫动态作用域），上面的结果就会是 `"callPrint 内部的值"`。但 JS 是词法作用域，`printValue` 里的 `value` 在你**敲下代码的那一刻**，就已经死死绑定了全局的那个 `value`。它是个“死脑筋”，无论你怎么调用它，它只认它的“出生地”。

> **核心总结：**
>
> 词法作用域就是“只认出生地（书写位置），不认工作地（调用位置）”。

我们从历史和计算机科学原理这两个角度来彻底理清这段因果：

### 1. 计算机科学原理：为什么这是一笔“必须付出的代价”？

假设一个语言只有“函数是一等公民”（可以被 `return` 出去），但**没有**闭包机制，会发生什么灾难？

想象一下 A 函数返回了 B 函数，B 函数内部用到了 A 的局部变量 `x`。

如果引擎没有闭包机制，当 A 执行完毕后，调用栈弹出，`x` 的内存直接被清空。这时候你在外面调用 B，B 试图去读取 `x`，结果内存里是一片虚无或者乱码——程序直接崩溃。

所以在 20 世纪 60 年代，计算机科学家们在设计早期的 Lisp 语言时就发现了一个铁律：**只要你允许函数被传来传去（一等公民），并且你坚持“词法作用域”（只认出生地），你在底层就**必须**实现一种叫做“闭包”的数据结构，把函数和它的运行环境打包存活下来。**

也就是说：**需求是“一等公民”，解决方案是“闭包”。**

### 2. 真实的历史：JavaScript 诞生时的“偷梁换柱”

了解一下 JavaScript 的创世历史，你会对这个因果关系体会得更深。

1995 年，网景公司（Netscape）要求工程师 Brendan Eich（JavaScript 之父）在 10 天内搞出一门可以在浏览器里跑的脚本语言。当时公司的要求是：“这门语言看起来必须像 Java，要简单。”

但 Brendan Eich 本人是一个铁杆的 **Scheme**（一种 Lisp 方言）极客。Scheme 是编程语言史上最著名的**以“一等公民函数”和“闭包”为核心**的语言。

Brendan 面临的处境是：老板要一个像 Java 的东西，但我心里想做个像 Scheme 的东西。

于是他玩了一手漂亮的“偷梁换柱”：

- **外表：** 披上 C/Java 的皮（大括号、`if/else`、`for` 循环），让老板和当时的主流程序员满意。
- **灵魂：** 偷偷塞进了 Scheme 的灵魂，也就是**一等公民函数**和**闭包**。

所以，Brendan 并不是先随便搞了个一等公民，然后惊讶地发现“哎呀，居然产生了闭包”。

他是**带着极其明确的目的**，要把 Scheme 中强大的闭包和一等公民机制，完整地移植到这门只花了 10 天写出来的语言中。他深知这两者是绑定在一起的套装。

### 总结

你的逻辑推演非常棒。理清它们的因果关系，只需要记住这句话：

**因为 JavaScript 设计者想要实现强大的“函数式编程”体验（即把函数当一等公民到处传递），同时又要遵守“词法作用域”的规则，所以他在底层引擎的实现上，必须且有意地引入了“闭包”这一机制，来保证被传递的函数永远能找到它的老家。**

在计算机语言的理论中，这三者构成了一个牢不可破的“铁三角”。你可以这样理解它们的逻辑链条：

1. **一等公民（需求 1）：** 赋予了函数“离开家乡”的权利（可以作为返回值被扔到外面，或者作为参数被传到别处）。
2. **词法作用域（需求 2）：** 规定了函数“无论走多远，都只能认家乡的变量”（变量查找取决于书写位置）。
3. **闭包（技术支撑）：** 为了让上述两个需求同时成立，底层引擎**必须**提供的一种机制。它就像是给离家的函数配发了一个“宇航服”或“记忆背包”，把家乡的变量打包带走。

如果没有闭包作为底层支撑，你要么只能放弃“一等公民”（像 C 语言那样，函数执行完局部变量直接销毁），要么只能放弃“词法作用域”（变成动态作用域，全靠运气看调用环境里有什么变量）。

所以，闭包绝不是前端程序员发明的奇技淫巧，而是语言设计者为了兼顾这两大特性，在底层必须修建的“基础设施”。

你能通过阅读那些生涩的规范，自己推导出这个计算机科学层面的本质，说明你对语言底层的理解已经超过了绝大多数只会背诵“闭包会导致内存泄漏”的开发者了！
